<objective>
Implement the D-07..D-12 artwork-identity migration mechanics: a deterministic, auto-running,
idempotent re-key of ARTIST artwork onto the Plan 02-02 collapsed identities (ART-01), plus the
building-block functions Plan 02-04 needs to apply human-confirmed ALBUM artwork recoveries (ART-02).

Purpose: artist identity is `md5(name)` — Plan 02-02 changes `name` for 36 of 124 artists, which
changes their id, which orphans any artwork already fetched under the old id. This plan is the
re-key that keeps ART-01 true: existing artwork must still resolve after the collapse, without
re-fetching (D-07/D-12).

For ART-02 (the 38 pre-existing orphaned album-artwork rows), live investigation on the Pi found
their exact provenance — CORRECTED from an earlier, wrong planning conclusion that the mapping was
unrecoverable (see `.planning/phases/02-artist-identity-artwork-migration/02-ORPHAN-PROVENANCE-CORRECTION.md`
for the full record). `sqlite3 library.db "SELECT type, source, COUNT(*) FROM artwork GROUP BY type,
source;"` shows all 38 orphans carry `source = 'backfill'`: they were written by the existing
`BackfillAlbumArtwork` (internal/infra/cache/backfill.go:25) — the startup repair routine that links
a JPG already on disk to an artwork row when enrichment saved the file but never inserted the row.
These are genuine, on-disk cover images (38/38 files present, ~61.5 MB total), orphaned later when
their album's identity (`md5(albumArtist‖album‖uri)`) changed underneath them — not corrupted or
unknown data. `md5` cannot be inverted, so the original (albumArtist, album, uri) string cannot be
recovered from the id alone, but the artwork ITSELF is still the real cover image, so identity can be
recovered by comparing pictures (perceptual hashing), not by reversing hashes. Plan 02-04 does that
comparison live on the Pi (fetching each of the ~40 currently-unlinked albums' cover via the local,
network-free `/albumart` endpoint, perceptual-hashing it, and matching against the 38 orphan files by
Hamming distance with a calibrated threshold + uniqueness guard) and produces a human-approved
mapping table. This plan's job is the safe, tested, idempotent, non-clobbering APPLY primitive Plan
02-04 calls once a pair is approved — it deliberately contains no image-comparison or
perceptual-hashing logic itself (that lives in Plan 02-04's Python tooling on the Pi, not this Go
package). The ROADMAP's own success bar for ART-02 is "toward 0", not "to 0" — matches below the
calibrated confidence threshold are correctly left unmatched rather than guessed.

Output: two new leaf-ish files under internal/infra/cache/ (same package, following the existing
backfill.go precedent), wired into the existing startup-migration hook, all unit-tested against
fixtures — no live Pi contact in this plan.
</objective>
