<objective>
Implement the D-07..D-12 artwork-identity migration mechanics: a deterministic, auto-running,
idempotent re-key of ARTIST artwork onto the Plan 02-02 collapsed identities (ART-01), plus the
building-block functions Plan 02-04 needs to apply human-confirmed ALBUM artwork recoveries (ART-02).

Purpose: artist identity is `md5(name)` — Plan 02-02 changes `name` for 36 of 124 artists, which
changes their id, which orphans any artwork already fetched under the old id. This plan is the
re-key that keeps ART-01 true: existing artwork must still resolve after the collapse, without
re-fetching (D-07/D-12).

For ART-02 (the 38 pre-existing orphaned album-artwork rows), this plan's own investigation during
planning found the historical (albumArtist, album, uri) triple behind each orphan's hash is NOT
mechanically recoverable: the orphaned files are dated 2026-05-14 (predating even the NAS→SSD move
this project's docs attribute them to — the Mac-hosted backend era), and a live brute-force test
against all 81 current albums × plausible historical path-prefix substitutions (NAS/USB swaps, with
NFC/NFD Unicode normalization variants) against all 38 live orphan hashes on the real Pi DB produced
ZERO matches. `md5` is one-way; without the exact historical strings, the id cannot be reconstructed.
So this plan does NOT attempt automatic album-orphan matching — it builds the safe, tested,
non-destructive APPLY mechanism, and Plan 02-04 supplies the match (via direct visual inspection of
the orphan images against the list of currently-unlinked albums, confirmed by the user before
anything is written). The ROADMAP's own success bar for ART-02 is "toward 0", not "to 0" —
consistent with this being a best-effort, evidence-based recovery rather than a guaranteed one.

Output: two new leaf-ish files under internal/infra/cache/ (same package, following the existing
backfill.go precedent), wired into the existing startup-migration hook, all unit-tested against
fixtures — no live Pi contact in this plan.
</objective>
